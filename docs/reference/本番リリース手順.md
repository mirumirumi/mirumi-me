# 本番リリース手順

Notion 移行の初回の本番リリース（WordPress から Notion の公開基盤への切り替え）と、そのあと WordPress を廃止するまでの手順。
切り替えが終わったあとの通常のリリースは、`Notion 公開基盤運用手順.md` の「application release と generate」を参照。

- 🚧 はまだ実装されていない予定のもの
- prd のリソースでまだ揃っていないものは `dev 環境と prd 環境の対照表.md` の 🚧 を参照
- 各コマンドの細かい挙動は `Notion 公開基盤運用手順.md` の該当する節を正とする

## 全体の流れ

1. 事前の確認（dev）
2. prd の準備
3. コメントの事前投入
4. 切り替え（順序厳守）
5. 切り替えのあとの片付け
6. WordPress の廃止まで

2 以降は prd を触るので、明示 GO のあとに行う。2 と 3 は、切り替えの当日より前に済ませておける。
切り戻しの手順はまだ決めていない（末尾の「切り戻し」）。

## 1. 事前の確認（dev）

済んだものには日付を書いておく。

- 新規公開、更新、非公開、重複 Webhook、途中失敗を実動確認する（2026-09-06 に済）
- Creators API を実 ASIN で確認する（済）
- 470 page の route uniqueness と generate を通す（済。2026-09-30 にも CI から通っている）
- dev の Notion データソースへ external WebP の canary を投入する。拒否された場合だけ Notion 用の JPEG / PNG fallback を追加する
    - WebP の本文画像（`smbc-nl`）と thumbnail（`my-home`）は、以前の API での投入で通っている。念のための確認
- コメントの公開フォームの異常系（Turnstile の token の期限切れ、二重送信、rate limit）と、`ゴミ箱` にしたときの非表示の経路を確かめる
- 本番のデータで render warning が出る記事を洗い出し、WordPress の本文で直しておく
    - prd では warning が 1 件でもあると、その記事の公開が失敗する。bootstrap では、その記事だけが飛ばされて旧 WordPress 版の HTML が残る
    - dev の Notion は旧変換で取り込んだままなので、dev のサイトの warning では本番を予測しきれない
    - 2026-10-01 に dev で数えたもののうち、本番でも出るはずなのは、もう存在しない記事やカテゴリーを指す内部ブログカード 15 件と、OGP を取れない外部ブログカード 1 件

## 2. prd の準備

### AWS / Cloudflare

- `CONTENT_CACHE` の KV namespace を作り、`server/wrangler.jsonc` の prd の `kv_namespaces` に ID を入れる（未設定だと deploy が通らない）
- 🚧 dev の `CONTENT_CACHE` から、X ポスト（`x-post:v4:*`）とブログカード（`bookmark:v1:*`）の cache を prd へ写す。残りの有効期限もそのまま引き継ぐ。写すためのスクリプトはまだない
    - 空のまま bootstrap すると、X ポスト約 100 件を xAI で解決し直すことになる（合計で数ドル、1 件最大 45 秒）。xAI はまれに解決に失敗し、prd ではその記事の公開が失敗になる
    - key に環境は入っていないので、dev の値をそのまま使える
- site bucket の `Referer` によるオリジン保護の値を、推測できないランダムな秘密値に変える。次の 3 段階で行う（Terraform）
    1. bucket policy で旧と新の両方の値を許可する
    2. CloudFront distribution の値を新しくする
    3. bucket policy を新しい値だけにする
- site bucket に `_internal/*` の Deny を入れる
- IAM ユーザー `mirumime-prd-publisher` のアクセスキーを発行し、prd の `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` に登録する（それまでは暫定で `S3_FullAccess_IAM` のキー）
- IAM ユーザー `mirumime-comment-digest` に prd 用の 2 本目のアクセスキーを発行し、prd の `SES_ACCESS_KEY_ID` / `SES_SECRET_ACCESS_KEY` に登録する
- そのほかの prd の secret を登録する。一覧は運用手順の「必須設定」
    - `NOTION_WEBHOOK_SECRET` は 4 の Webhook subscription を作るまで値が決まらない。`secrets.required` の確認で deploy が止まる場合は、仮の値を入れておく
- dev / prd の bucket、CloudFront、KV、Secrets と Access policy を確認する

### Notion

prd の posts / pages / comments は、dev のデータソースを複製して作り直す。formula、ボタン、テンプレート、カラム幅などの見た目の調整まで、dev で整えたものをそのまま持っていくため。

dev の Notion の調整をすべて終えてから行う。複製したあとに dev だけを調整しても prd には入らないので、そのときは両方に入れる。3 のコメントの事前投入よりも前に行う（あとで作り直すと、事前投入したコメントも消える）。

- dev の posts / pages / comments を複製し、名前から `(dev)` を外す
- 複製で変わる ID と変わらない ID
    - data source ID は新しくなる。わかるのは複製した直後。3 のコメントの事前投入（`config.ts`）と、4 の手順 6 の prd の deploy（`wrangler.jsonc`）より前に、次の 3 か所を新しい ID にしてコミットしておく
        - `server/wrangler.jsonc` の prd の `NOTION_{POSTS,PAGES,COMMENTS}_DATA_SOURCE_ID`。`server/worker-configuration.d.ts` は `wrangler types --env-interface=CloudflareBindings` で作り直す
        - `tools/migrate-to-notion/src/config.ts` の prd
        - `dev 環境と prd 環境の対照表.md`
    - property ID は維持される（dev を prd から複製したときに `internal-state` で確認済み）。複製したあと、実際の ID が dev と一致していることを確認する
        - `NOTION_INTERNAL_STATE_PROPERTY_ID` はそのままでよい
        - `NOTION_COMMENT_*_PROPERTY_ID` は、prd にも dev と同じ値を入れる（空のままだと、コメントの Webhook が無視される）
- relation とボタンの向き先を確認する。dev を向いたまま複製されていると、prd の操作で dev の row を作ったり参照したりしてしまう
    - posts の `category` が共用の categories を向いている（片方向の relation なので、複製しても categories 側にプロパティは増えない）
    - comments の `親コメント` が、複製した comments 自身を向いている
    - comments のボタン `返信` の「ページを追加」先が複製した comments 自身で、テンプレート「みるみ」（comments の既定のテンプレート）も複製した側のものを使っている
- posts / pages の formula の URL を prd に変える。複製した直後は dev を向いている
    - `プレビュー`：`https://mirumi-me-dev.v2p04rubfuwnvttj.workers.dev/preview?pageId=` → prd の Worker（`https://mirumi-me-prd.v2p04rubfuwnvttj.workers.dev/preview?pageId=`）
    - `開くボタン`：`https://d3694gpnjd4x49.cloudfront.net/`（dev の CloudFront）→ `https://mirumi.me/`
- 複製で入ってきた dev のテスト用の row（posts / pages / comments）をすべて消す
    - 手元に prd の `upload-state.json` / `comments-import-state.json` が残っていたら、一緒に消す。残っていると、消した row がまだあるものとして upload / import が動く
- integration の接続を確認する
    - 複製したデータソースに dev の integration（`workers-api (dev)`）がついていたら外す
    - prd の integration（`workers-api`）が prd の posts / pages / comments と共用の categories にだけ接続していて、`(dev)` のデータソースには接続していないことを確認する
- 旧 prd の posts / pages / comments は prd の integration から外す。切り替えが終わったら消す

## 3. コメントの事前投入

全件の投入には時間がかかるので、切り替えの前に一度入れておく。最終的な差分は 4 で入れる。

```bash
cd tools/migrate-to-notion
bun run fetch-comments
bun run import-comments --dry-run  # 計画だけ出す
bun run import-comments
bun run verify-comments
```

- 投入先は `MIGRATION_TARGET` で決まり、既定は prd
- state は `comments-import-state.json`。export はメールアドレスを含むので git に入れない
- 再実行しても同じ row は作らない。hash が変わった row は更新し、承認済みから外れた row は `ゴミ箱` にする

## 4. 切り替え

この順序で行う。

**手順 11 のマージまで、`main` へは push しない。**

- bootstrap より前に `project/datsu-wordpress` を `main` にマージすると、新しい CI の generate が先に走って publish index ができてしまい、`last-deploy` を初期化できる bootstrap が二度と通らなくなる
- マージ前の `main` には、旧 `deploy.yml`（WordPress から Nuxt generate して `aws s3 sync --delete` する）が残っている。切り替えのあとにマージ以外で `main` へ push すると、新しい配信物が旧サイトで上書きされ、`_internal/*`（publish index など）も消える

1. WordPress で記事を更新しないようにし、コメントの投稿も止める（切り替えのあいだ、コメントフォームは maintenance 表示にする）
2. 画像を正規化してから、記事と固定ページを投入する

    ```bash
    cd tools/migrate-to-notion
    bun run fetch
    bun run normalize-media
    # report と preview mapping を確認し、unresolved の static image が 0 件なら実画像を追加する
    bun run normalize-media --apply
    bun run dry-run
    bun run upload
    ```

    - `fetch` は省略しない。手元の `contents.ndjson` / `media-attachments.ndjson` は過去に取ったときのままで、WordPress の本文はそのあとも直していることがある。手順 1 で更新を止めてから取り直すことで、最新の本文が投入される
    - `normalize-media --apply` だけが media の S3 へ、`upload` だけが Notion へ書く
    - `upload` の state は `upload-state.json`、mapping は `media-mapping.json`
    - 投入後の Notion の画像 URL に、`-1999x...` などの WordPress の寸法サフィックスが残っていないことを確認する
3. コメントの差分を入れる。コマンドは「3. コメントの事前投入」と同じで、WordPress 側の全件と hash で照合される
4. 目次リンクを置き換える

    ```bash
    bun run --cwd tools/migrate-to-notion fix-toc-anchors --apply
    ```

5. prd の `/preview?pageId=` で画像の表示を mirumi.me（旧 WordPress の配信）と見比べる。dev では確認できていないため
    - `android-app`（縮めたスクショ）、`comics`（漫画の引用画像 415px）、`pc-freesoft` / `firefox-plugin`（インラインのアイコン）、`albumartwork-puttogether`（縮めた画像 + alt）
    - 小さい画像が本文幅まで引き伸ばされていないこと
6. prd の Worker を手元から deploy し、Container の rollout が落ち着くのを待つ

    ```bash
    cd server
    bun run deploy:prd
    # LAST MODIFIED が deploy 時刻より後になり、それ以上動かなくなったら rollout は終わっている
    bunx wrangler containers list --env prd
    ```

7. bootstrap を流す

    ```bash
    bun run generate:prd -- --mode bootstrap --dry-run  # instance ID と payload だけ確認する
    bun run generate:prd -- --mode bootstrap           # yes の入力を求められる
    ```

    - publish index が空なので全記事の thumbnail 生成が走り、数時間かかる（Workflow の polling は最大 12 時間）。止まって見えても落とさない
    - 進捗は site bucket の `_internal/jobs/<workflowId>.json` に出る
    - 終わるまで Notion の記事を触らない。bootstrap は、途中で触られた記事が 1 本でもあると job ごと止まる
8. mirumi.me で確認する
    - Notion で 🔴 の記事がないこと。bootstrap で失敗した記事は `下書き` に戻り、`公開エラー` が「bootstrap で失敗しました: 」で始まる。直して `公開` を押せば、Notion の `公開日` のまま公開される
    - HTML、OGP、画像、payload、カテゴリ、一覧、sitemap、feed
    - コメント。550 件ある `just-answer` と、`<a>` を含む旧コメント 42 件（`pc-freesoft` / `vivaldi` / `auto-music-create` / `just-answer` / `out-of-body` など）の表示
    - OGP 画像が壊れていた 36 記事が直っていること（一覧は `.contexts/壊れたサムネイル一覧.md`）
    - Amazon の商品カード
9. bootstrap に含まれた記事で partial publish を 1 回通し、publish index の読み取り権限まで確認する
10. Webhook subscription を作る（詳しくは運用手順の「Webhook subscription の初回設定」）
    - 購読するイベントは `page.properties_updated` と `page.created`
    - Access 配下の `GET /admin/notion-webhook-verification` で verification token を取り、Notion の確認画面に貼ってから、同じ値を prd の `NOTION_WEBHOOK_SECRET` に登録する
11. `project/datsu-wordpress` を `main` にマージする。以降は `main` への push で `deploy.yml` が deploy を行い、サイトの生成物に効く変更があるときだけ generate まで流す
    - bootstrap はコミットを持たず generate の基準にならないので、このマージの run では generate が 1 回余分に走る（害はない）

## 5. 切り替えのあとの片付け

- 暫定で使っていた `S3_FullAccess_IAM` のアクセスキーを無効化する
- GitHub Actions の secret から、AWS 系と `GPG_PASSPHRASE` を削除する。消すと旧 `deploy.yml` で旧サイトを作り直す経路も使えなくなるので、切り戻しの方針を決めてから消す
- S3 に残っている `feed-comments.xml` を削除する
- prd の Cron で、定期バックアップ（04:00 JST）とコメントの digest（09:00 JST）が動いたことを確認する
- Terraform の CI は default branch にある workflow しか動かないので、`main` へのマージのあとに動くことを確認する

## 6. WordPress の廃止まで

切り替えのあとも、検索と PV は WordPress に依存している。次がすべて終わってから WordPress（mirumi.in）を廃止する。

- 🚧 検索 API と検索画面の切り替え（今は `app/src/pages/s.vue` が `/wp/v2/search` を呼んでいる）
- 🚧 PV の送信を Analytics Engine へ切り替え、`tools/site-admin-extension` を Notion と Analytics Engine の SQL API へ切り替える（PV は Analytics Engine から読み、「編集」リンクは Notion のページを開く）
    - 拡張の Notion integration（読み取りだけ）を、2 で作り直した prd の posts / pages に接続する。2026-10-02 時点では dev の posts / pages にだけ接続してある
    - 拡張が読む data source ID を prd のものにする
    - token は `tools/site-admin-extension/.env.local` にある（Cloudflare の API token と Notion の integration token）
- いいねの UI と WordPress の endpoint 呼び出しの削除（2026-10-01 に `ShareButtons.vue` を削除して済）
- 🚧 `app/src/app.config.ts` の `mirumi.in` / WordPress の `baseURL` の削除
- repository、生成 HTML、browser の実通信に WordPress の endpoint が残っていないことを確認する
- `tools/migrate-to-notion` 直下の、git ignore された生成物を削除する（`Notion 移行 やること.md` の「移行スクリプト」）
- `.contexts/` に残している移行用のファイル（`実装の進捗状況.md`、`Workers API 実装計画.md`、`コメント基盤 実装作業メモ.md`、移行用のデータ一覧 4 つ、text-align のバックアップ）を整理する。それまでは消さずに取っておく

## 切り戻し

- 🚧 切り戻しの手順。本番リリース手順を詰めるときに、ちゃんと考える
    - 2026-10-01 に、場合分け（切り替えの途中、全面的な切り戻し、コードの不具合だけ戻す）と、コードだけでは戻らないものの下書きを `.contexts/移行の残り 整理メモ.md` の「切り戻しの論点」に書いた。手順にする前に、もう一段精査する

考えるときの材料として、今の状態をまとめておく。

- 配信の経路（DNS、CloudFront、S3 のウェブサイトエンドポイント）は、切り替えの前後で変わらない。変わるのは site bucket の中身と、media bucket に足される正規化済みの画像（旧 object は消さない）
- site bucket には S3 versioning を入れていないので、bootstrap で上書きした object を直前の版に戻す手段はない。bootstrap は全削除はせず、生成したものだけを上書きする
- 旧サイトを作り直せるのは、`main` の旧 `deploy.yml`（`workflow_dispatch` でも動く）だけ。WordPress から Nuxt generate して `aws s3 sync` する
    - 最後の sync は `--delete` 付きで、除外は `_nuxt/*` / `apps/*` / `assets/components/*` だけなので、`_internal/*`（publish index など）も消える
    - GitHub の secret（AWS 系と `GPG_PASSPHRASE`）を使うので、「5. 切り替えのあとの片付け」でそれを消すと使えなくなる
    - 手順 11 で `project/datsu-wordpress` を `main` にマージすると、`main` の `deploy.yml` は新しいものに置き換わる
    - push で動く workflow は、その commit にあるファイル。手順 11 のマージを revert した commit を `main` に push すると、旧 `deploy.yml` が動く
    - 古い action（`actions/checkout@v3`、`actions/setup-python@v4` の Python 3.9、`aws-actions/configure-aws-credentials@v1`）に依存している。2026-09-30 の `main` への push では成功しているが、GitHub 側の廃止で動かなくなるおそれはある
- 切り戻しても、prd の Worker と Notion の Webhook subscription は残る。そのまま Notion で `公開` やコメントの承認をすると、新しい基盤が site bucket に書き込む
- WordPress（mirumi.in）は、切り替えのあとも記事とコメントの書き込みを止めた状態で動いている。コメント基盤の設計書では、Notion 側で受けた新規コメントを捨てて WordPress へ戻すことはしない方針
- publish index があると、bootstrap は実行できない（`validateBootstrapIndex`）。切り戻してから切り替えをやり直すなら、publish index（`_internal/publish-index-v1.json`）と Notion の `last-deploy` の扱いも決める必要がある
