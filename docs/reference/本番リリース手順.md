# 本番リリース手順

Notion 移行の初回の本番リリース（WordPress から Notion の公開基盤への切り替え）と、そのあと WordPress を廃止するまでの手順。
切り替えが終わったあとの通常のリリースは、`Notion 公開基盤運用手順.md` の「application release と generate」を参照。

- 🚧 はまだ実装されていない予定のもの
- prd のリソースでまだ揃っていないものは `dev 環境と prd 環境の対照表.md` の 🚧 を参照
- 各コマンドの細かい挙動は `Notion 公開基盤運用手順.md` の該当する節を正とする

## 全体の流れ

1. 事前の確認（dev。最後に `project/datsu-wordpress` を `dev` にマージし、dev を入れ直して、3〜4 の投入から bootstrap までを dev で通す。途中で 2 の「Notion」の複製も行う）
2. prd の準備
3. コメントの事前投入
4. 切り替え（順序厳守）
5. 切り替えのあとの片付け
6. WordPress の廃止まで

2 以降は prd を触るので、明示 GO のあとに行う。ただし 2 の「Notion」の複製は、1 の「dev の入れ直し」の中で dev を空にした直後に行う（2026-10-10 に圭くんが決めた）。2 と 3 は、切り替えの当日より前に済ませておける。
切り戻しの手順は末尾の「切り戻し」。

    - 2026-10-04 に、10/3 に取り直した本文で数えた結果は 3 件。どれも WordPress の本文の Amazon のショートコードで、引用符が崩れていた（2026-10-04 に圭くんが WordPress で直した）

### `dev` へのマージ

dev の入れ直しの前に、`project/datsu-wordpress` を `dev` にマージする（PR は squash でマージしてよい）。

- `dev` の `deploy.yml` が新しいものになり、以降は `dev` への push で dev 環境に deploy される。prd には何も起きない（`main` の旧 `deploy.yml` は、`main` への push でしか動かない）

#### 用意するもの

どこかに登録するものはなく、手元で使うだけ。コマンドはエージェントに流してもらう前提で、秘密の値はチャットに貼らずに、ファイルとログインで渡す（エージェントのシェルは呼び出しごとに作り直されるので、`export` では残らない）。

- 前日まででよい：`tools/migrate-to-notion/.env.dev` を作り、次の 2 行を書く。ルートの `.gitignore` の `.env.*` で git には入らない

    ```
    MIGRATION_TARGET=dev
    NOTION_TOKEN=<workers-api (dev) の Internal Integration Secret>
    ```

    - token は、Notion の integration の設定画面（`https://www.notion.so/profile/integrations`）で `workers-api (dev)` を開き、Configuration からコピーする
    - コマンドは `bun --env-file=.env.dev run <script>` で流す。`--env-file` の値は、`bun run` が起動するスクリプトまで届く。`.env.dev` という名前は Bun が自動では読まないので、付け忘れると `NOTION_TOKEN` がなくて止まる（Notion には書かない）
    - 投入先と token を同じファイルに置くので、dev の token のまま prd に向けたり、その逆をしたりしにくい
    - 人の token では入れない。dev の Webhook は integration が作った row の `page.created` を無視するが、人の token で入れると、コメント 1 件ごとの `page.created` がそれぞれ comment-refresh を起動する
- 当日、始める前：圭くんが自分のターミナルで `aws login` する。ブラウザでのサインインが要るので、エージェントにはできない。同じマシンの `~/.aws` を見るので、エージェントのシェルからもそのまま使える
    - 使うのは `normalize-media --apply`（media bucket への書き込み）と、手順 1 の `aws s3 rm`
    - `normalize-media` は SDK の既定の経路で `~/.aws` の profile（credential_process）から認証情報を取り、期限が来たら取り直す。キーを発行したり、環境変数に書き出したりしなくてよい。書き込み先の bucket と region は `tools/migrate-to-notion/src/config.ts` にある
- `ssh conoha-wing` が、パスフレーズなどの入力なしで通ること（`ssh -o BatchMode=yes conoha-wing true`。2026-10-10 に通った）。`fetch` と `fetch-comments` が WordPress の DB から読む（読むだけ）
- Notion の UI での操作は圭くんの手。エージェントは、手順 1 の row の全削除と、手順 2 の複製・名前の変更・ボタンや formula の直し・integration の接続のところで止めて頼む
- 手順 5 の bootstrap の起動には、Cloudflare の API token が要る。手元の wrangler のログイン（OAuth）では Workflow を起動できないため（運用手順の「手元から generate を投げる」）
    - 当日までに圭くんが作る。権限は CI の deploy token と同じ `Workers Scripts Edit` と `Containers Edit` で、対象の account だけに絞り、有効期限を数日にしておく
    - 運用手順の決まりどおりファイルには保存しない。起動のコマンドだけを、圭くんが自分のターミナルで token を渡して流す（手順 5）。dry-run と、起動したあとの進み具合の確認は、エージェントが OAuth のまま行える
    - 4 の手順 7 の prd の bootstrap も同じ。終わったら revoke する

#### 手順

1. 消す
    - dev の generate が走っていないことを確かめてから始める。`dev` への push のあとは、CI の generate が 30 分前後走っていることがある。generate は Notion から読み、最後に `_internal/` へ publish index を書く
    - dev の posts / pages / comments の row を、Notion で全選択してすべて消す
        - categories は prd と共用なので触らない
        - データソースのテンプレート（comments の「みるみ」など）は row ではないので残る
    - `tools/migrate-to-notion` の dev の state（`upload-state.full.json` / `upload-state.smoke.json` / `comments-import-state.dev.json`）を消す。残っていると、消した row がまだあるものとして upload / import が動く
    - dev の site bucket の `_internal/`（publish index、公開 snapshot、job の進捗）を消す。publish index があると bootstrap が断る

        ```bash
        aws s3 rm s3://mirumime-dev-mirumi-me/_internal/ --recursive
        ```

        - `_internal/` のほかは消さない。`assets/components/`（Prism の言語ファイル）のように、generate では作られない object がある。消えた slug の古い HTML は dev に残るが、どこからもリンクされないので害はない
    - 残すもの
        - dev の KV（`CONTENT_CACHE`）。中身は X ポスト、ブログカード、Amazon の cache だけで、page には紐づいていない。残せば xAI での解決をやり直さずに済む
        - バックアップ（R2 と S3）
2. prd の Notion を複製する。2 の「Notion」を上から順に行う
    - 2 の「複製で入ってきた dev のテスト用の row をすべて消す」は要らない（dev は空）
    - prd の data source ID の直し（`server/wrangler.jsonc`、`tools/migrate-to-notion/src/config.ts`、`dev 環境と prd 環境の対照表.md`）は、手順 5 の bootstrap が終わるまで `dev` に入れない。`wrangler.jsonc` の変更は CI で generate まで流れ、publish index がないあいだは失敗する。作業ブランチに置いておき、bootstrap のあとに `dev` へ入れる
3. 入れ直す。3 と、4 の手順 2〜4 を、同じ順で dev に向けて行う（4 の手順 3 のコメントの差分は、事前投入の直後なので省いてよい）

    ```bash
    cd "$(git rev-parse --show-toplevel)/tools/migrate-to-notion"
    bun --env-file=.env.dev run fetch-comments
    bun --env-file=.env.dev run import-comments --state comments-import-state.dev.json --dry-run
    bun --env-file=.env.dev run import-comments --state comments-import-state.dev.json
    bun --env-file=.env.dev run verify-comments
    bun --env-file=.env.dev run fetch
    bun --env-file=.env.dev run normalize-media
    bun --env-file=.env.dev run normalize-media --apply
    bun --env-file=.env.dev run dry-run
    bun --env-file=.env.dev run upload --state upload-state.dev.json
    bun --env-file=.env.dev run fix-toc-anchors --apply
    ```

    - `import-comments` と `upload` には、必ず `--state` で dev 用のファイルを渡す。既定の `comments-import-state.json` / `upload-state.json` は prd 用で、そこに dev の分が入っていると、prd の投入で dev の row が投入済みとみなされる
    - dev の Webhook は integration が作った row の `page.created` を無視するので、投入のあいだ止めなくてよい
    - `normalize-media --apply` は dev / prd 共用の media bucket に書く。すでにある object は書き換えずに足すだけなので、4 の手順 2 でもう一度流しても、そのあいだに増えた画像の分だけが足される
4. 4 の手順 5 の画像の見比べを、dev の `/preview?pageId=` で行う
5. bootstrap を流す。`generate:dev` はリポジトリのルートの `package.json` にあるので、ルートで流す（`tools/migrate-to-notion` にいるままだと「Script not found」になる）

    ```bash
    cd "$(git rev-parse --show-toplevel)"
    bun run generate:dev -- --mode bootstrap --dry-run  # instance ID と payload だけ確認する（OAuth のままでよい）
    CLOUDFLARE_API_TOKEN=<token> bun run generate:dev -- --mode bootstrap  # 圭くんが自分のターミナルで流す
    ```

    - 起動のコマンドは Workflow を起動したらすぐ終わる。完了は待たない

    - かかった時間を書き留めて、4 の手順 7 の見積もりにする。進捗は site bucket の `_internal/jobs/<workflowId>.json` に出る
    - 終わるまで Notion の記事を触らない。publish index がないあいだは、dev の generate も `公開` も「publish index が存在しません」で失敗する。そのあいだは `dev` に push しない（生成物に効く変更があると、generate まで流れて失敗する）。deploy が要るなら、generate を `skip` にして dispatch する
6. 4 の手順 8 と同じ項目を dev のサイトで確かめる。つまずいたところや直した手順は、この手順書の 3〜4 に反映する
7. 手順 2 で作った prd の data source ID の直しを `dev` に入れる

## 2. prd の準備

### AWS / Cloudflare

- `CONTENT_CACHE` の KV namespace を作り、`server/wrangler.jsonc` の prd の `kv_namespaces` に ID を入れる（未設定だと deploy が通らない）
- dev の `CONTENT_CACHE` から、X ポスト（`x-post:v4:*`）とブログカード（`bookmark:v1:*`）の cache を prd へ写す。上の `kv_namespaces` に prd の id を入れてから、bootstrap より前に行う

    ```bash
    bun run copy-content-cache --dry-run  # 件数だけ出す（2026-10-04 の dev は 159 件）
    bun run copy-content-cache            # yes の入力を求められる
    ```

    - wrangler のログインで動く（`wrangler kv` を使う）。namespace は `wrangler.jsonc` の `CONTENT_CACHE`（dev / prd）から引く
    - 残りの有効期限はそのまま引き継ぐ。残りが 2 分を切っているものと、prd にすでにある key は写さない（prd で解決し直した値を、古い dev の値で戻さないため）
    - 空のまま bootstrap すると、X ポスト約 100 件を xAI で解決し直すことになる（合計で数ドル、1 件最大 45 秒）。xAI はまれに解決に失敗し、prd ではその記事の公開が失敗になる
    - key に環境は入っていないので、dev の値をそのまま使える
- site bucket の `Referer` によるオリジン保護の値を、推測できないランダムな秘密値に変える。次の 3 段階で行う（Terraform）
    1. bucket policy で旧と新の両方の値を許可する
    2. CloudFront distribution の値を新しくする
    3. bucket policy を新しい値だけにする
- site bucket に `_internal/*` の Deny を入れる
- IAM ユーザー `mirumime-prd-publisher` のアクセスキーを発行し、prd の `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` に登録する（それまでは暫定で `S3_FullAccess_IAM` のキー）
- IAM ユーザー `mirumime-comment-digest` に prd 用の 2 本目のアクセスキーを発行し、prd の `SES_ACCESS_KEY_ID` / `SES_SECRET_ACCESS_KEY` に登録する
- そのほかの prd の secret を登録する。一覧は運用手順の「必須設定」
    - `NOTION_WEBHOOK_SECRET` は 4 の Webhook subscription を作るまで値が決まらない。`secrets.required` の確認で deploy が止まる場合は、仮の値を入れておく
- dev / prd の bucket、CloudFront、KV、Secrets と Access policy を確認する

### Notion

prd の posts / pages / comments は、dev のデータソースを複製して作り直す。formula、ボタン、テンプレート、カラム幅などの見た目の調整まで、dev で整えたものをそのまま持っていくため。

1 の「dev の入れ直し」の中で、dev の row を消した直後に行う（2026-10-10 に決定し、同じ日に済。新しい data source ID は `dev 環境と prd 環境の対照表.md`、旧 prd の 3 つは `(old)` に改名した）。dev の Notion の調整は、それまでに終えておく。複製したあとに dev だけを調整しても prd には入らないので、そのときは両方に入れる。3 のコメントの事前投入よりも前に行う（あとで作り直すと、事前投入したコメントも消える）。

- dev の posts / pages / comments を複製し、名前から `(dev)` を外す
- 複製で変わる ID と変わらない ID
    - data source ID は新しくなる。わかるのは複製した直後。3 のコメントの事前投入（`config.ts`）と、4 の手順 6 の prd の deploy（`wrangler.jsonc`）より前に、次の 3 か所を新しい ID にしてコミットしておく。`dev` に入れるのは、dev の入れ直しの bootstrap が終わってから（1 の「dev の入れ直し」の手順 2）
        - `server/wrangler.jsonc` の prd の `NOTION_{POSTS,PAGES,COMMENTS}_DATA_SOURCE_ID`。`server/worker-configuration.d.ts` は `wrangler types --env-interface=CloudflareBindings` で作り直す
        - `tools/migrate-to-notion/src/config.ts` の prd
        - `dev 環境と prd 環境の対照表.md`
    - property ID は維持される（dev を prd から複製したときに `internal-state` で確認済み）。複製したあと、実際の ID が dev と一致していることを確認する
        - `NOTION_INTERNAL_STATE_PROPERTY_ID` はそのままでよい
        - `NOTION_COMMENT_*_PROPERTY_ID` は、prd にも dev と同じ値を入れる（空のままだと、コメントの Webhook が無視される）
- relation とボタンの向き先を確認する。dev を向いたまま複製されていると、prd の操作で dev の row を作ったり参照したりしてしまう
    - posts の `category` が共用の categories を向いている（片方向の relation なので、複製しても categories 側にプロパティは増えない）
    - comments の `親コメント` が、複製した comments 自身を向いている
    - comments のボタン `返信` の「ページを追加」先が複製した comments 自身で、テンプレート「みるみ」（comments の既定のテンプレート）も複製した側のものを使っている
- posts / pages の formula の URL を prd に変える。複製した直後は dev を向いている
    - `プレビュー`：`https://mirumi-me-dev.v2p04rubfuwnvttj.workers.dev/preview?pageId=` → prd の Worker（`https://mirumi-me-prd.v2p04rubfuwnvttj.workers.dev/preview?pageId=`）
    - `開くボタン`：`https://d3694gpnjd4x49.cloudfront.net/`（dev の CloudFront）→ `https://mirumi.me/`
- dev を空にした直後に複製するので、dev のテスト用の row は入ってこない。複製したデータソースに row があったら消す
    - 手元に prd の `upload-state.json` / `comments-import-state.json` が残っていたら消す。残っていると、消した row がまだあるものとして upload / import が動く
- integration の接続を確認する
    - 複製したデータソースに dev の integration（`workers-api (dev)`）がついていたら外す
    - prd の integration（`workers-api`）が prd の posts / pages / comments と共用の categories にだけ接続していて、`(dev)` のデータソースには接続していないことを確認する
- 旧 prd の posts / pages / comments は prd の integration から外す。切り替えが終わったら消す

## 3. コメントの事前投入

全件の投入には時間がかかるので、切り替えの前に一度入れておく。最終的な差分は 4 で入れる。

```bash
cd "$(git rev-parse --show-toplevel)/tools/migrate-to-notion"
bun --env-file=.env.prd run fetch-comments
```

## 4. 切り替え

この順序で行う。

**手順 11 のマージまで、`main` へは何も入れない。**

1. WordPress で記事を更新しないようにする。コメントの投稿は止めない
    - コメントの投稿先が Workers に変わるのは、手順 7 の bootstrap で mirumi.me が新しいフロントに入れ替わったとき。それまでに WordPress に来たコメントは、手順 11 のマージの前に拾う

4. 目次リンクを置き換える

    - HTML、OGP、画像、payload、カテゴリ、一覧、sitemap、feed
    - コメント。550 件ある `just-answer` と、`<a>` を含む旧コメント 42 件（`pc-freesoft` / `vivaldi` / `auto-music-create` / `just-answer` / `out-of-body` など）の表示

    - Amazon の商品カード
9. bootstrap に含まれた記事で partial publish を 1 回通し、publish index の読み取り権限まで確認する
10. Webhook subscription を作る（詳しくは運用手順の「Webhook subscription の初回設定」）
    - 購読するイベントは `page.properties_updated` と `page.created`
    - Access 配下の `GET /admin/notion-webhook-verification` で verification token を取り、Notion の確認画面に貼ってから、同じ値を prd の `NOTION_WEBHOOK_SECRET` に登録する
11. `dev` → `main` のリリース PR を、マージコミットありでマージする（squash しない）。以降は `main` への push で `deploy.yml` が deploy を行い、サイトの生成物に効く変更があるときだけ generate まで流す
    - squash すると、切り戻しで `dev` に積んだ revert が `main` に入らなくなる（末尾の「切り戻し」）。`dev` → `main` の PR を開くと、`release-pr-reminder.yml` がマージコミットでマージするようコメントする
    - マージの前に、手順 3 のコメントの差分をもう一度入れる（コマンドは同じ）。手順 3 から bootstrap が終わるまでに WordPress に来たコメントが入り、このマージの run の generate で記事に載る。入るのは承認済みだけなので、WordPress で承認してから流す
    - bootstrap はコミットを持たず generate の基準にならないので、このマージの run では generate が 1 回余分に走る（害はない）

## 切り戻し

場合は 3 つに分かれる。

- A. 切り替えの途中（4 の手順 1〜10。`main` へのマージの前）
- B. 全面的な切り戻し（4 の手順 11 のあと。Notion をやめて WordPress に戻す）
- C. 部分的な切り戻し（新しい基盤のまま、コードの不具合だけを戻す）

### 前提

- 配信の経路（DNS、CloudFront、S3 のウェブサイトエンドポイント）は、切り替えの前後で変わらない。変わるのは site bucket の中身と、media bucket に足される画像だけ
- site bucket には S3 versioning を入れていないので、bootstrap で上書きした object を直前の版に戻す手段はない。旧サイトは作り直して戻す
- 旧サイトを作り直せるのは、`main` の旧 `deploy.yml` だけ。WordPress から Nuxt generate して `aws s3 sync --delete` し、CloudFront を invalidation する
    - 除外は `_nuxt/*` / `apps/*` / `assets/components/*` だけなので、`_internal/*`（publish index など）も消える。そのため、もう一度切り替えるときも bootstrap から通せる
    - prd に向くのは、ref が `main` のときだけ。ほかのブランチで動かすと dev の bucket と distribution に向く
    - push で動く workflow は、push した commit にあるファイル。1 の「`dev` へのマージ」の commit を `dev` で revert して `dev` → `main` をマージすると、`main` の `deploy.yml` が旧版に戻って動く
    - `dev` に revert を入れただけでは何も動かない。revert した commit の `deploy.yml` は旧版で、`dev` への push を trigger にしていない
- コメントの投稿先は、site bucket にあるフロントで決まる。旧サイトに戻れば、また WordPress に送られる

### 戻せなくなる地点

次のどれかを越えたら全面的な切り戻し（B）はできないので、前向きに直す。

- 「5. 切り替えのあとの片付け」で、`S3_FullAccess_IAM` のキーを無効化するか、GitHub の secret（AWS 系と `GPG_PASSPHRASE`）を消したとき。旧 `deploy.yml` はこのキーと secret を使う
- 「6. WordPress の廃止まで」を終えて、WordPress を止めたとき
- 旧 `deploy.yml` が依存する古い action（`actions/checkout@v3`、`actions/setup-python@v4` の Python 3.9、`aws-actions/configure-aws-credentials@v1`）が、GitHub 側で廃止されたとき。2026-09-30 の `main` への push（18 分）では動いている

### A. 切り替えの途中

1. 手順 10 の Webhook subscription を作っていたら、止める（下の B の 1）
2. 手順 7 の bootstrap が走っていたら、終わるのを待つ
3. bootstrap が site bucket を書き換えたあとなら、`main` の旧 `deploy.yml` を dispatch して旧サイトを作り直す。bootstrap の前なら要らない

    ```bash
    gh workflow run deploy.yml --ref main
    ```

4. WordPress の記事の更新を再開する
5. もう一度切り替えるときは、4 の手順 1 からやり直す。手順 2〜3 で prd の Notion に入れた row の扱い（消して入れ直すかどうか）は、そのときに決める

### B. 全面的な切り戻し

1. 新しい基盤が site bucket に書かないように、Notion の Webhook subscription を止める
    - Notion の integration の設定で subscription を消すか、prd の `NOTION_WEBHOOK_SECRET` を消す（Worker が 500 を返し、何も起動しない）
    - 生きていると、旧サイトを作り直す前に Notion で `公開` やコメントの承認をしたとき、新しい基盤が site bucket に書く。作り直したあとは publish index が消えているので、公開もコメントの反映も「publish index が存在しません」で失敗して書かないが、失敗が続くだけなので止めておく
2. 走っているものがないことを確かめる。旧 `deploy.yml` には concurrency の設定がないので、新しい基盤の書き込みと並んで走り、あとから終わったほうに上書きされうる
    - GitHub Actions の `deploy` に、走っている run がないこと（generate の job は Cloudflare の Workflow の完了を待っている）
    - Cloudflare の Workflow に、running / queued の instance がないこと

        ```bash
        cd server
        bunx wrangler workflows instances list mirumi-me-publish-prd --status running
        bunx wrangler workflows instances list mirumi-me-publish-prd --status queued
        bunx wrangler workflows instances list mirumi-me-comment-refresh-prd --status running
        bunx wrangler workflows instances list mirumi-me-comment-refresh-prd --status queued
        ```

3. 1 の「`dev` へのマージ」の commit を、`dev` で revert する（その PR の画面の Revert ボタンで revert の PR を作って `dev` に入れるか、`git revert <commit>` を `dev` に入れる）
4. `dev` → `main` のリリース PR を、マージコミットありでマージする。旧 `deploy.yml` が動いて、WordPress から旧サイトを作り直す
    - `dev` に revert のほかの未リリースの変更があれば、それも一緒に出る。出したくないものは先に `dev` から外しておく
5. 確かめる
    - mirumi.me が WordPress 版の表示に戻っていること。コメントのフォームから WordPress に投稿できること
    - site bucket の `_internal/` が消えていること（もう一度切り替えるときの bootstrap の前提）
6. WordPress の記事の更新を再開する
7. site-admin-extension を、revert したあとの tree（WordPress を読む版）で build し直し、Chrome に読み込み直す

コードを戻しても戻らないもの：

- 切り替えのあとに Notion で書いた記事と、Workers で受けたコメントは WordPress にない。手で戻すか諦める（コメント基盤の設計書では、Notion 側で受けたコメントを WordPress へ戻さない方針）
- Notion の期間の PV は Analytics Engine にだけあり、WordPress の PV には入らない
- prd の Worker と Cron は残る。Cron（バックアップ、コメントの digest、止まった公開の通知）は site bucket に書かないので、害はない。Webhook を止めたあとに Notion で `公開` を押すと、30 分後に止まった公開の通知が来る
- media bucket は、正規化した画像などが増えただけで、旧サイトが指す WordPress 時代の object は消していない。孤立した object を消す仕組みを作るときは、WordPress を廃止するまでそれらを消さない

もう一度切り替えるとき：

- 3 の revert を `dev` で revert してから、4 をやり直す。同じ commit をマージし直しても、revert で消した変更は戻らない（Git は取り込み済みとして覚えている）
- `_internal/` は 4 の sync で消えているので、bootstrap を通せる。Notion の `last-deploy` は bootstrap が初期化し直す
- 切り戻しているあいだに WordPress で書いた記事と受けたコメントは、4 の手順 2〜3 で入れ直す。prd の Notion に残っている row の扱いは、そのときに決める

### C. 部分的な切り戻し

ふだんのリリースと同じ流れで戻す。不具合を入れた commit を `dev` で revert し、dev 環境で確かめてから、`dev` → `main` をマージする。generate は公開中の全記事を今のコードで作り直すので、不具合のあるコードで公開した記事も直る。

コードを戻しても戻らないもの：

- データの形。次のものの形を変える変更は、revert したコードで読めなくなる。形を変えるときは後方互換にするか、key の version（`-v1`）を上げて並べる
    - site bucket の publish index、published-pages の snapshot、app manifest、検索インデックス（`_internal/search-index-v1.json`）
    - KV の cache の値（`published-post-slugs:v2`、`published-routes:v1`、`app-store:v1` など）
    - Analytics Engine に書く data point の形（site-admin-extension が読む）
- Notion：property の追加や改名と、書き戻した値（`公開日`、`更新日`、`公開エラー` など）
- Durable Object の migration：`wrangler.jsonc` の `migrations` を revert すると class の削除になりうる。revert せずに前向きに直す
- コードの外の設定：secret、Access、Webhook subscription、KV namespace、Terraform（apply は別の経路）
- `公開待ち` / `非公開待ち` の記事は generate が触らないので、ボタンを押し直す
