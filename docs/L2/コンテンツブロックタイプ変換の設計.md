# コンテンツブロックタイプ変換の設計

WordPress の本文を Notion のブロックへ変換するとき（`tools/migrate-to-notion/src/convert.ts`）と、Notion のブロックを HTML にするとき（`shared/src/render.ts`）の判断の理由と、踏んだ罠を書く。
何をどのブロックにするかは L1 の `コンテンツブロックタイプ変換方針.md` を正とする。

## 意図的に移行しなかったもの

### about と profile の表の microdata

2026-10-03 に圭くんと決めた。

- about は Organization（name、brand、founder、address、email、contactPoint、description、publishingPrinciples）、profile は Person（name、jobTitle、hasCredential、knowsAbout）を、表の `itemscope` / `itemprop` で持っていた
- Notion のテーブルは属性を持てないので変換で落ちる。誰も気づかないまま落ちていたのを 2026-10-03 に見つけ、そのまま落とすと決めた
- 理由
    - Organization は、組織の識別やロゴ・ナレッジパネルのためのもので、検索結果の見た目は変わらない。個人ブログで効く場面はほぼない
    - 書き方もゆるく（Brand や founder に name がない、contactPoint がただの文字列）、もともと Google に使われていたか疑わしい
- やるなら、profile.vue に ProfilePage（mainEntity が Person、sameAs に X・GitHub・note など）の JSON-LD を足す。Google はブログの About Me ページも対象に挙げている。本番前の必須ではない

### A8 のバナー

- 2026-10-03 に圭くんが WordPress 側で消した（5 記事・8 個）。今後もアフィリエイトのバナーは貼らない方針
- 消す前は、枠ボックスの 1 段落目に `<a href="https://px.a8.net/…"><img src="https://www21.a8.net/svt/bgt?…"></a>` があり、変換で `[image name="bgt"]` になって `https://mirumi.media/bgt`（403）を指していた（下の「インライン画像のショートコードは mirumi.media 専用」）
- dev の Notion には壊れたまま残っている（2026-09-16 の import のため）。本番は import の前に `fetch` し直すので入らず、dev もリリース前の入れ直し（`本番リリース手順.md` の「dev の入れ直し」）で消える

## インライン画像のショートコードは mirumi.media 専用

- 段落の途中、コールアウトや引用の 1 段落目、リスト、表のセルにある `<img>` は、`[image name="…"]` として本文に残す。name はファイル名だけで、render は `https://mirumi.media/<name>` を組み立てる
- そのため外部の画像がこの位置に来ると壊れる。2026-10-03 時点の WordPress の本文で該当したのは上の A8 のバナーだけで、消したので 0 件になった
- 外部の画像が段落にそれ 1 つだけで置かれていれば、image ブロック（external）になって表示される。拡張子のない URL でも image ブロックにできることは確認済み

## Notion に入れると変わるもの

変換が送ったものと、Notion が返すものが違うことがある。変換のテストはリクエストしか見ず、render のテストは期待する形を直接渡すので、どちらのテストでも気づけない。新しい種類のブロックや属性を変換に足すときは、dev に入れて API で取り直した姿を確かめる。

2026-10-03 にコールアウトの icon とリンクの `+` を見つけ、圭くんの依頼で全記事を点検した（下の「全記事の往復点検」）。

### 全記事の往復点検（2026-10-04）

- やり方：当日に `fetch` し直した WordPress の本文を今の変換で変換し、どのデータソースにも属さない一時ページの下へ `upload.ts` と同じ分け方（`planBlockBatches`）で入れ、取り直して比べた。送ったフィールドがすべて同じ値で返るか、子の数と並びが同じかを見た。プロパティは posts と同じ型の一時データベースで比べた（category の relation は除いた）。終わったあと一時ページはゴミ箱へ入れた
    - dev の posts と比べなかったのは、dev が古い変換と古い本文で入っていて、変換や本文の差が混ざるため
- 結果：470 件すべて投入でき（validation error は 0）、差分は次の 4 種類だけだった。ブロックの種類・並び・子の数、装飾と色、数式（文字サイズ）、コールアウトの icon（枠の Notion のアイコンを含む）、キャプションのトークン、画像・動画・音声・embed・bookmark の URL、テーブル、コードの言語、タイトル・slug・もくじ・thumbnail は一致した
    - リンクのクエリの書き直し（139 個）。下の「リンクのクエリを Notion が書き直す」
    - リンクの `source` パラメータの削除（3 個）。同じく下
    - 改行コード：コードブロックの本文（190 個 / 54 記事）と、プロパティの カスタム CSS（2 件）の `\r\n` が `\n` になる。表示は変わらない
    - 日付の秒：`公開日` と `更新日` は秒が切り捨てられ、`2016-06-13T01:54:00.000+09:00` の形で返る。画面は日付しか出さない。同じ分に公開された記事が 4 組あり（django-multi-word-search と lambda-layers など、技術ブログを統合したときの記事）、その組の中の並びは WordPress と変わりうるが、一覧は同じ日時なら slug 順に並べるので不安定にはならない

### コールアウトの icon を省略すると 💡 が付く

- Block API では icon を外せない。作成でも更新でも `icon: null` は 400 になる
- Markdown API（`PATCH /v1/pages/{id}/markdown`）で新しく作ったコールアウトだけは `icon: null` になる。既存のコールアウトは、Markdown で丸ごと書き換えても icon が残る（ブロック ID と中身は保たれる）
- UI で icon を外したコールアウトは、API で `icon: null` が返る
- Notion のアイコン（`type: "icon"` で `{ name, color }`）は Block API で付けられる。2026-10-03 に通った name は square、square-alternate、square-dashed、archive、document、clipboard、bookmark、chat、list、circle、minus、pin、flag、tag、card、window、folder、inbox、package、grid、table、checkmark、check、comment、speech-bubble。color は gray、lightgray、brown、yellow、orange、green、blue、purple、pink、red
- 影響：変換は L1 どおり枠ボックスを icon なしで作っていたため、2026-09-16 に import した dev ではすべて 💡 になり、info ボックスとして描画されていた（2026-08-26 時点の WordPress で 308 個 / 133 記事）。dev はリリース前の入れ直しで直る

#### 枠ボックスの目印は Notion のアイコン 1 つにした

2026-10-03 に圭くんと決めた。

- 枠ボックスは Notion のアイコンの square-alternate（lightgray）にする（`shared/src/content.ts` の `WAKU_CALLOUT_ICON`）。変換はこれを付け、render はこれのときだけ枠ボックスにする。アイコンは圭くんが UI で選んだもの
- 絵文字ではなく Notion のアイコンにしたのは、絵文字だと render の「💡 ♻️ 🚨 以外の絵文字は枠の本文の先頭に出す」に例外を足すことになるため。Notion のアイコンは API で絵文字と別の種類として返るので、区別がはっきりしている
- 「Notion のアイコンならどれでも枠」にしなかったのは、Notion 上で見た目がばらばらになり、あとで混乱するため（圭くんの懸念）。将来 Notion のアイコンで別の箱を作りたくなったときの余地も残る。色まで一致を求めるのも同じ理由
- 覚えにくさは警告で補う。決めたアイコン以外の Notion のアイコン、icon なし、カスタム絵文字や画像のアイコンは render の warning になり、中身は枠ボックスで出したうえで、正しいアイコンを文面で教える。prd では公開が止まる
- 「icon なし」も warning にしたのは、Markdown API や UI で外したものを枠として通すと、枠の作り方が 2 通りになってそろわないため

### リンクのクエリを Notion が書き直す

- Notion はリンクの URL のクエリを書き直して返す。クエリを読み取った結果（`URLSearchParams` の中身）は変わらない
    - `+` が `%20` になる。A8 の `a8mat=35975J+2JORXU+3606+OEZIP` が `a8mat=35975J%202JORXU%203606%20OEZIP` で返る（全記事で 129 個 / 78 記事、2026-10-04 時点の本文）
    - そのほか、`/` が `%2F`（linksynergy の `id=Q6/…`）、`[]` が `%5B%5D`（`shop[]=`）、値の中の `:` `/` `?` などが `%3A` などになる
- `source` という名前のパラメータは消される。2026-10-03 に 40 個の名前で試し、消えたのは `source` だけだった（`tag`、`utm_*`、`a8mat`、`ref`、`linkCode`、`ascsubtag` などは残る）。全記事で該当したのは Google の検索とリダイレクトの URL 3 個（cat-get、mfa-app、smbc-nl）で、消えても飛び先は変わらない
- クエリの中では `+` と `%20` はどちらも空白の意味なので、実害はない。2026-10-04 に圭くんが dev で `%20` になった A8 のリンク（motton-compare）を踏み、公式サイトへ飛べることを確かめた
- キャプションやショートコードなど、ただの文字列の中の URL は変わらない（`[button]` の `url` は `+` のまま）

## Notion の HTML ブロック（未対応）

2026-07 に Notion に入った。2026-10-03 に mirumi.me のワークスペースで、API から作って取り直すところまで確かめた。採用するかは決めていない。

- API では、アップロードした `.html` ファイルを持つ embed ブロックとして返る。`embed` は `caption` と `url` だけで、HTML ブロックだと示す項目はない。Notion がホストする URL で、path が `.html` / `.htm` で終わることで見分ける
- `url` は 1 時間で切れる署名付き URL。取ってきた中身はアップロードしたものとバイト単位で一致した
- 普通の embed として `<iframe src="署名付き URL">` にすると、プレビューでは表示され公開も 🟢 になるが、1 時間ほどで 403 になる。HTML に限らず、Notion にアップロードしたファイルを持つ embed（PDF など）はすべて同じ
- そこで 2026-10-03 から、render はこれを warning にしている（圭くんの依頼）。HTML ブロックについて調べたことを未来の圭くんが忘れて `/html` を使っても、prd では公開が止まって 🔴 になり、dev とプレビューでは 🚨 の箱が出る
    - 採用するときは、この warning を外し、公開のときに HTML を取ってきて本文に差し込むか、S3 にコピーして iframe にする処理を入れる
    - Notion にアップロードした audio / video も同じく署名付き URL だが、これは公開のときに S3 へコピーする（2026-10-04 に実装。L2 `Notion 公開基盤の設計.md` の「Notion にアップロードした audio / video」）ので、このガードには含めていない

## アプリ紹介カードを App Store の URL から組み立てる

2026-10-04 に実装した（L1 の `コンテンツブロックタイプ変換方針.md` のアプリ紹介カード、`Notion 移行 やること.md`）。動きは運用手順の「アプリ紹介カード」。

- 公開のとき、Container が iTunes を直接引き、cache は Worker の KV に置く（Container からは橋渡し `bindings.internal/app-store-cache` で読み書きだけを頼む）。ブログカードの cache は 30 日で引き直すが、アプリは価格が変わりうるので 7 日にした（夜のあいだの仮決め）
    - はじめはブログカードや X ポストと同じく、Worker が iTunes を引いていた。2026-10-04 に dev で試すと、Worker からの lookup は 55 回中 48 回が 403 だった（成功 7 回）。手元から同じ URL を引くと、User-Agent の有無にかかわらず 200 だった
    - Workers の外への通信は、多くのサーバーで分け合う IP から出る（Cloudflare 公式ブログ「Cloudflare servers don't own IPs anymore」）。iTunes の lookup は IP ごとに回数を制限しており、20 回 / 分より少なくても 403 が出るという報告が Apple のフォーラムに多い。Cloudflare Workers からだけ Apple の別の API（verifyReceipt）が断られるという報告もある（返信なし）
    - Containers の出口の IP は公式のドキュメントにも GitHub の説明にも書かれておらず、Workers と別だという根拠は見つからなかった。そこで圭くんの提案で、コードを変えずに確かめた：記事の thumbnail に lookup の URL を外部リンクとして入れて `公開` を押すと、Container がそれを取りに行く。3 回中 3 回とも 2xx が返った（画像ではないので「image 以外の応答」で失敗する）。Worker の成功率で 3 回続けて成功する確率は 0.2% ほど
    - Container から通る理由（IP が違うのか、Workers の fetch に付く `CF-Worker` ヘッダーが無いからか）はわかっていない。Container からも断られるようになったら、AWS の Lambda 経由で引くか、書くときに手元で引いて焼き込む運用を考える
- 引く対象は、段落の `[app …]` で `ios` があり、`name` か `icon` が無いものだけ（`shared/src/enrichment.ts` の `collectAppStoreUrls`）。移行した 103 件は焼き込んであるので引かない
- 書いた属性を優先して、足りないものだけを引いた値で埋める（夜のあいだの仮決め）。価格だけ手で書き換える、のような使い方ができる
- アイコンは Container が取ってきて `MediaNormalizer.normalizeBodyImage` で mirumi.media に置き直す。移行の 103 件で「Google / Apple の CDN 直リンクだと将来切れる」として webp にしたのと同じ考え方。名前は `app-icon-<ID>` にした
- 属性の読み方（`parseShortcodeAttributes`）は render と enrichment で同じものを使うよう、`shared/src/shortcode.ts` に移した
- Worker のプレビュー（`/preview`）はブログカードと同じく外部を引かないので、`ios` だけのカードは 🚨 の箱になる
- バッジの画像は、はじめアプリーチの配布元（`nabettu.github.io`、作者の GitHub Pages）を直接指していた。render が指していた `as_ja.svg` は配布元から消えていて（404）、移行した 103 件も含めて全部のカードで画像が壊れていた（2026-10-04 に dev で圭くんが気づいた）。WordPress 版は `itune_ja.svg` を使っていたので、いったんそちらに直し、2026-10-05 に圭くんの判断で mirumi.media に写して置いた（他人の置き場所に頼らないため）
- WordPress 版のカードにあった「posted with アプリーチ」の行は出さない。もう使っていないサービスへのクレジットなので外したままにするのを Claude が提案し、2026-10-05 時点で圭くんから反対はない
- WordPress 版がアプリ名で作っていた Google Play の検索リンクは出さず、`android` を書いたときだけ出す（2026-10-05 に圭くんと決めた。Android 版のリンクは圭くんが書く）
