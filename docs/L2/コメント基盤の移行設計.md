# コメント基盤の移行設計

> 2026-09-02 に書いた設計で、2026-09-04 のレビューで実測値の訂正と spam 非移行を反映した。
> 2026-09-21〜22 の実装で変えた点は末尾の「実装時の変更」にまとめてあり、本文より優先する。
> 運用上の確定事項は `docs/reference/Notion 公開基盤運用手順.md` の「コメント」節が正。

## 結論

- 保存先は private な Notion `comments` データソースで問題ない。現在の 3,097 件なら、全件 query は 31 request、最多記事の部分 query は 6 request に収まる
- Nuxt は Notion も Worker も読まない。Container がコメントを取得して `BuildPage.comments` に入れ、コメント本文を静的 HTML と payload に焼き込む
- 承認・返信は既存公開 Workflow / Container の「記事 1 本の部分公開」を再利用する。ただし記事公開 action とは分けた `comment-refresh` とし、一覧・XML は更新しない
- コメントだけの再 build では、Notion 上の未公開の記事編集を混ぜないよう、S3 に保存した最後の公開済み `BuildPage` snapshot を土台にする
- 移行対象は承認済みコメントだけにする。spam と trash は移さない
- 既存コメント import は記事 import と別の再開可能な command にする。初回 bulk は事前に流し、最終切り替えでは WordPress の書き込みを止めて差分照合する。同じ cutover 内では実行するが、記事 import の 1 transaction には混ぜない
- メールアドレスは全件を平文のまま `comments` データソースに置く。暗号化も別データソースへの分離も行わない。条件はデータソースを圭くん以外へ共有しないことと、build manifest に載せないことの 2 つ
- コメント feed は復活させない

## Notion を保存先にできる根拠

Notion API は 1 connection あたり平均 3 request/秒、data source query の `page_size` は最大 100。現在の件数なら、全 build で 31 request（rate quota だけの下限は約 10.4 秒）、最多記事の部分 build で 6 request（同約 2 秒）である。

一方、移行は最低でも 3,097 create request が必要である。既存 migration と同じ 400 ms 間隔でも待機だけで約 20 分 39 秒かかるため、最終 cutover で初めて全件投入しない。

本文は page child block ではなく `rich_text` property に置く。child block にすると build 時にコメントごとの追加 fetch が必要になる。`text.content` 1 個の上限は 2,000 文字なので、5,555 文字を 2,000 文字以下の rich text object に分割する。実データ最大は 3 object で収まる。

### `comments` の最小 schema

| property | type | 用途 |
| --- | --- | --- |
| `投稿者名` | title | 空なら `匿名` |
| `記事 slug` | rich_text | 記事対応の正規 key。slug 変更禁止の公開契約を利用する |
| `legacy-post-id` | number | WordPress 由来だけ。private 記事を含む対応確認用 |
| `親コメント` | self relation（one-way） | 親 1 件。reverse relation は作らない |
| `本文` | rich_text | source text を欠損なく保持 |
| `本文形式` | select | `wordpress-html` / `plain-text` |
| `投稿日時` | date | WordPress は `comment_date_gmt` から同じ瞬間を保存 |
| `メールアドレス` | email | 非公開 PII。WordPress の空文字は値なしとして保存する |
| `状態` | select | `pending` / `approved` / `spam` / `trash`。移行で入るのは `approved` だけ |
| `管理者コメント` | checkbox | 旧 `user_id = 1` または圭くんの返信 |
| `出所` | select | `wordpress` / `public-form` / `owner` |
| `legacy-comment-id` | number | 既存 anchor と import 冪等 key |
| `コメント ID` | unique_id | 新規コメントの public ID。prefix は `c` |
| `request-id` | rich_text | 新規投稿の重複防止 key |
| `通知日時` | date | digest 送信済み判定 |
| `反映エラー` | rich_text | comment refresh の最新エラー。成功時に空へ戻す |

記事との実行時対応は不変な slug を正とする。Container が slug で解決できれば足り、page ID の作り直しにも追随しなくてよいため、posts への relation は持たない。

コメント側に公開可否の概念は持ち込まない。その slug が publish index にあるかどうかだけで公開が決まるので、非公開記事のコメントを保持するための実装は要らない。`jemtc` の 56 件も `legacy-post-id` と slug で対応を維持したまま移行し、slug が publish index に無いので公開されない。将来 `jemtc` を Notion で公開すれば、そのまま出るようになる。

既存コメントの public ID は decimal の `legacy-comment-id`、新規コメントは Notion の Unique ID プロパティとする。したがって既存の `#comment-123` は変わらず、新規は `#comment-c-42` のような短い連番になる。prefix は数字だけの legacy ID と衝突しないよう `c` を使う。親 relation は build 時に同じ public ID へ正規化する。

Unique ID は auto-increment で API からは読めるだけで更新できない。プロパティ自体は Notion UI で追加する。移行 bulk 後に追加すると既存 3,097 行にも採番されるため、新規コメントは 3,098 付近から始まるが、値の連続性に意味はないので問題にしない。公開フォームは受付成功を返すだけで ID を返さないため、create response に Unique ID が含まれるかどうかには依存しない。

## 公開データと build

公開用 `BuildComment` は次だけを持つ。

```ts
interface BuildComment {
  id: string
  parentId: string | null
  authorName: string
  createdAt: string
  contentHtml: string
  isOwner: boolean
}
```

- `状態=approved` だけを対象に、`投稿日時`、public ID の順で安定 sort する
- `wordpress-html` は現行 `CommentBase.vue` の `formatContent()` と同じ変換を再現する。行の連なりを `<p>` で包み、単独改行を `<br />` にし、裸の URL を `rel="nofollow ugc"` 付きの `<a>` にしたうえで、許可 tag / attribute だけへ sanitize する。sanitize は現行にない処理なので、`<a>` を含む 42 件は表示が変わりうる
- `plain-text` は HTML escape 後に同じ段落変換と linkify を行う
- どちらも `contentHtml` にしてから manifest へ入れる
- メール、Notion property の raw response、status、request ID は manifest、Nuxt payload、HTML、log に入れない
- full / bootstrap は approved を全件 query して slug ごとに group する。通常の記事部分公開と comment refresh は対象 slug で絞る。どちらも `filter_properties` で公開に必要な property だけを受け取る
- query の 429 は `Retry-After`、503 は exponential backoff に従う。全 page を取り切れない、schema が違う、親が欠ける場合はコメント 0 件へ縮退せず build を失敗させる
- ただし publish index に無い slug の group は失敗扱いにせず捨てる。`jemtc` のような非公開記事のコメントがこれにあたる
- `BuildPage.comments` を `articles/{pageId}.json` に書き、`[post].vue` から `CommentList` へ渡す。Nuxt generate 中と browser runtime のコメント fetch は 0 件にする
- ローカル dev はコメントを扱わない。`notion-content.ts` の `createBuildPage` には常に空の `comments` を渡し、`CommentList` は 0 件表示にする。dev で Notion からコメントを取得する実装は作らない

### コメントだけを更新するとき

既存の article partial publish は Notion article が `公開待ち` であることを前提とするため、そのまま呼ばない。また、現在の Notion 本文を再取得すると未公開の編集まで公開してしまう。

通常の記事公開が成功するたび、コメントを含む公開済み `BuildPage` を content-addressed な `_internal/published-pages-v1/{pageId}/{contentHash}.json` に保存し、publish index の `contentHash` から現在版を特定できるようにする。snapshot は Notion の代替正本ではなく、S3 で現在配信中の状態を再 build するための派生物である。古い snapshot は `_nuxt` の hash asset や旧画像と同じく自動削除しない。`_internal/*` は CloudFront から取得できないため、増えるのは容量だけである。

`comment-refresh` は次の順にする。

1. comment row の slug を publish index で解決し、公開中の記事 1 本であることを確認
2. index が指す公開済み `BuildPage` snapshot を読む
3. Notion からその slug の approved comments を一括取得し、`comments` だけを置き換える
4. generate 直後に同じ集合の hash を再確認し、途中変更があれば deploy しない
5. 新しい content-addressed snapshot を先に保存する
6. 記事の `index.html` と `_payload.json` だけを S3 へ置き、CloudFront もその route だけ invalidation して、publish index を最後に更新

publish index で更新するのは `contentHash` と `deployedAt` だけにする。`deployedNotionEdit` は記事本文の版を指す値で、`preparePageRevision` の非公開 retry 判定と公開時の競合検出がこれに依存しているため `comment-refresh` では変更しない。posts 行にも何も書き戻さない。書き戻すと `last-edited-by` が `workers-api` になり、未公開の記事編集が残っていても `status` が 🟢 公開中 に変わってしまう。

トップ、カテゴリ、sitemap、通常 feed はコメントで変わらないため更新しない。

ただし現在の実装はこうならないので、`comment-refresh` 用の分岐が要る。`createSiteBuildPlan` は `changedPages` に post が 1 件でもあれば aggregate route をすべて plan に入れ、`generateSite` は毎回 sitemap と feed を出力し、`selectDeployKeys` と `createInvalidationPaths` は partial でも XML を常に通す。`comment-refresh` では aggregate route を plan に入れず、XML の生成・配置・invalidation も省く。

通常の記事公開と full build は、その時点の approved comments も必ず同じ `BuildPage` に含める。

## 投稿 API と Turnstile

公開 route は `POST /api/comments` だけにし、公開 GET は作らない。

```json
{
  "slug": "article-slug",
  "parentId": "123 or notion-page-id or null",
  "authorName": "匿名",
  "authorEmail": "mail@example.com",
  "content": "plain text",
  "requestId": "uuid",
  "turnstileToken": "token"
}
```

- slug は publish index 上の公開中 post だけを許可する。page ID、status、日時、`isOwner` は client から受け取らない
- parent は同じ slug の approved comment だけを許可する
- 本文は 1〜5,555 文字、名前とメールも Notion の size limit 内で検証する
- 専用 rate limit を IP 単位で置き、CORS / Origin は `FRONTEND_ORIGIN` のみにする。ただし Origin は認証とはみなさない
- Workers の rate limit binding は Cloudflare の location ごとに独立した permissive なカウンタで、グローバルな上限ではない。スパム対策の主役は Turnstile であり、rate limit は補助と位置づける
- Turnstile は server-side Siteverify を必須とし、`success` に加えて production の hostname と action を照合する。token は 5 分・single-use なので、成功・失敗後とも widget を reset する
- local validation と既存 `request-id` の確認後に Turnstile、Notion create の順で処理する。Siteverify の `idempotency_key` にも `request-id` を使う。Notion への保存が確認できてから受付成功を返し、不明時の再試行は同じ `request-id` で重複を避ける。ただし Notion に一意制約はないため、同じ `request-id` がほぼ同時に 2 本届けば両方 create されうる。実質の重複防止は Turnstile token が single-use であることに依存している
- request body、メール、Turnstile token を log に出さない

## 承認・返信

- 公開投稿は `状態=pending`、`出所=public-form` で作る
- Notion の「承認」button は `状態=approved`、「非表示」は `pending` または `spam` へ変える。row 自体は削除しない
- 圭くんの返信は親と slug を引き継ぎ、`approved`、`管理者コメント=true`、`出所=owner` で新しい row を作る
- Notion webhook の event payload には data source ID が入らないため、property ID で振り分ける。property ID はデータソース内で一意なので、comments の `状態` / `本文` / `投稿者名` / `親コメント` の ID を posts の `internal-state` と同じ方式で env に持たせ、`updated_properties` と照合する。マッチしたときだけ page を再取得して `comment-refresh` を起動するので、無関係な更新で Notion を叩かない
- `page.created` も最初からハンドルする。この event には `updated_properties` がないため property ID で振り分けられず、page を 1 回取得して comments 行かどうかを判定する。page の作成頻度は低く、公開フォーム経由の作成は `状態=pending` で即座に何もせず終わるため、この取得コストは許容する
- こうしておけば、Notion UI でテンプレートから一度にプロパティを埋めて作り `page.properties_updated` が飛ばない場合でも取りこぼさない。webhook subscription で `page.created` を有効にすることを初回設定の手順に含める
- `page.deleted` はハンドルしない。削除済み page は再取得できず slug を特定できないため、row を削除せず `trash` にすることを運用ルールとし、誤って削除したときは full build で収束させる
- event は順不同・集約されうるため payload を状態として使わず、必ず最新 row を読む。Workflow instance ID には event ID を使う
- `通知日時` や `反映エラー` だけの更新は webhook から無視して loop を防ぐ
- refresh 失敗時も desired state は Notion の `状態` に残し、`反映エラー` を表示する。次の retry / full build で再収束させる

## 1 日 1 回の通知

- 09:00 JST の Cron で `出所=public-form AND 通知日時 is empty` を query し、0 件なら送らない
- digest は件数、記事 slug、投稿者名、本文冒頭、Notion row link を載せる。投稿者メールは載せない
- 宛先（`COMMENT_DIGEST_RECIPIENT`）へ送信成功後、対象 row の `通知日時` を更新する。mark 失敗は翌日の重複通知を許容し、通知漏れを避ける
- 移行行と owner reply は import / create 時点で通知済みにする

通知 transport は AWS SES とする。Cloudflare Email Routing は受信専用で送信に使えず、Cloudflare Email Service は送信元 domain を Cloudflare DNS に置く必要がある一方 `mirumi.me` の DNS は AWS にあるため、通知のためだけに DNS を移さない。

SES は sandbox のまま使う。宛先が圭くんの outlook.com アドレス 1 つに固定なので、送信元と宛先の両方を verified identity にすれば sandbox 解除は要らない。送信元はドメインではなく単一のメールアドレスを verify すれば足り、DNS 設定も DKIM 設定も不要になる。sandbox の 1 日 200 通・毎秒 1 通の上限は 1 日 1 回の digest に対して十分である。

`ses:SendEmail` と固定 sender / recipient だけを許す専用 credential を Workers Secrets に置く。既存 AWS credential を流用しない。

## メールアドレスの扱い

平文のまま `comments` に置くことは決定済み。ただし次の access policy を前提とする。

- comments database は shared page / teamspace 配下に置かず、Notion Site 公開もしない
- 閲覧者は圭くんと、この database を明示共有した専用 integration だけ
- view でメール列を隠すことは access control とみなさない。database を共有すれば閲覧権限を持つ人はメールにも到達できる前提にする
- 将来ほかの人へ comments database を共有するなら、その前にメールだけを別の private data source へ分離するか暗号化する
- Notion token には必要な comments / posts だけを共有し、backup も private な R2 / S3 に限定する

## 移行 run

### 事前 bulk

1. 本番 comments schema と access を作り、件数・状態・記事分布の基準 report を保存
2. DB から必要 field だけを SSH stdout で取得する。公開 endpoint や server 上の一時 export file は使わない
3. `legacy-comment-id` を key に、親が先になる topological order で承認済み全件を create する。本文は 2,000 文字以下へ分割する
4. state file に Notion page ID と source hash を原子的に保存し、再実行は同じ row を作らない
5. 保存するのは承認済みだけとし、spam と trash は移さない。private `jemtc` の 56 件は保持するが、slug が publish index に無いので公開 manifest には入らない

### 最終 cutover

1. 圭くんの最後の WordPress 記事更新後、旧 WordPress comment POST を停止する。切り替え中の form は maintenance 表示にする
2. WordPress を再 export し、事前 bulk との差分だけでなく全 `legacy-comment-id` の hash を照合する。新規・編集・承認を反映し、承認済みから外れた row は hard delete せず `trash` にする。WordPress は spam を 30 日で自動削除するため、`comment_approved = 1` に無いことを圭くんが消した証拠としては扱わない
3. 記事の最終 import とコメント差分 import は別 state / command で実行するが、同じ cutover checklist の完了条件にする
4. comments を含む full build と新しい投稿 form / API を deploy する
5. 検証完了まで WordPress は書き込み停止のまま保持し、rollback 可能にする。Notion 側で受けた新規コメントを捨てて WordPress へ戻さない
6. 完了条件を満たしてから WordPress と旧 endpoint を廃止する

## 完了条件

- 最終 snapshot と Notion が承認済み件数、記事別件数、本文・日時・投稿者・メール、親関係の hash で一致する。メールは WordPress の空文字と Notion の値なしを同値として比較する
- 公開対象の全 comment public ID が生成 HTML に 1 回ずつあり、既存 `#comment-{legacy-id}` がすべて到達できる
- depth 5 / 6 を含む全件を描画し、インデントだけ depth 4 で止まる（現行実装の挙動を維持する）
- 550 件の記事で HTML / payload / 表示を確認し、generate 中・browser ともコメント取得通信がない
- 既存コメントの段落・改行・linkify が現行表示と一致する。`<a>` を含む 42 件だけは sanitize による差分を目視確認する
- コメント取得失敗、cursor 取りこぼし、親欠損、途中更新は deploy を止め、旧 S3 object と publish index を維持する
- 承認、非表示、owner reply、本文編集が対象記事 1 本だけを更新し、記事の未公開編集を混ぜない
- Turnstile の正常、期限切れ、duplicate、hostname / action 不一致、rate limit を実動確認する
- digest の 0 件時、送信成功、送信失敗、送信後 mark 失敗を確認する

## 実装時の変更

2026-09-21〜22 の実装で上の設計から変えたもの。実装中の作業メモ（`.contexts/`）から移した。

### 構成

- comment-refresh は `PublishWorkflow` に mode を足すのではなく、別クラス `CommentRefreshWorkflow`（binding `COMMENT_REFRESH_WORKFLOW`）にした。publish 側の複雑な validation / writeback 分岐を汚さないため。Container の job queue は共有し、直列実行は維持
- Worker から publish index を読む経路が無かった（S3 は Container だけが読める）。`POST /api/comments` の slug 検証のため、Worker 側に WebCrypto の SigV4 署名で `GetObject` する小さな実装を置き、公開中 post slug の集合を `CONTENT_CACHE` に短時間 cache する。cache miss の slug は 1 回だけ S3 を読み直してから拒否する
- comment-refresh の S3 配置は「記事の `index.html` と `_payload.json` だけ」ではなく、partial publish と同じく hash 付き `_nuxt/*` と app manifest の和集合も置く。Container image が最後の full build より新しいと、HTML が参照する asset が S3 に無くなるため。集約 route と XML は置かない・invalidation しない
- full / bootstrap でも published-pages snapshot を全 page 分保存する。保存しないと index の `contentHash` が指す snapshot が無く、comment-refresh が動かないため

### データと schema

- property 名と select の option は、日本語化と posts との表記の統一で設計から変わった。現在の名前は `shared/src/notion-comments.ts` の `COMMENT_PROPERTIES` と `*_LABELS` が正
    - 例：`状態` → `status`、`出所` → `from`、`メールアドレス` → `email`、`コメント ID` → `id`、`記事 slug` → `slug`、`投稿日時` → `投稿日`、`通知日時` → `通知日`、`反映エラー` → `公開エラー`
    - `status` の option は `承認待ち` / `承認済み` / `スパム` / `ゴミ箱`、`from` は `WordPress` / `公開フォーム` / `管理者`、`本文形式` は `WordPress HTML` / `プレーンテキスト`
- `親コメント` を one-way の self relation にすると、Notion では対称になる（子に親を入れると親にも子が入る）。そのため `子コメント` を逆側に持つ dual relation にした。コードは `親コメント` だけ読む
- Unique ID の prefix は、Notion が 1 文字を拒否したので `CM` にした。public ID は `c-N` のまま
- `parentId` は設計の JSON 例にある Notion page ID ではなく、public ID（`123` または `c-42`）だけを受ける。client には Notion page ID を出さないため
- 本文の CRLF は LF に正規化して保存・hash する（Notion が `\r` を保持するか不明なため）
- `投稿者名` は、公開フォームでは空なら `匿名` を保存する（現行フォーム踏襲）。import は source のまま保存し、render 側で `匿名` に倒す
- `本文形式` / `投稿日` が空の row（Notion UI で作った owner reply など）は `プレーンテキスト` / `created_time` に倒す
- Notion の date property は秒を切り捨てるので、移行の hash 照合は分の精度にした
- HTML sanitize の allowlist は実データから決めた：`a[href rel target]` `strong` `b` `em` `i` `del` `s` `ruby` `rt` `rp` `ul` `ol` `li` `blockquote` `code` `br` `p`

### build

- 「親が欠けたら build 失敗」はやめた（2026-09-21 圭くんの要望）。build は slug の row を状態を問わず読み、approved だけ描画する。非表示の親を持つ子は最も近い表示中の先祖へ、row 自体が無い親を持つ子は root へつなぎ直す。別記事・ID 欠損・重複・循環は従来どおり失敗
- comment row の `slug` を後から変えた場合、旧記事側は次の build まで古いコメントが残る（許容）

### 承認・返信

- owner reply は入力を本文だけに寄せた。row のボタン `返信` がテンプレート「管理者の返信」で `status=承認待ち` の page を作り、書き終えたら圭くんが `承認済み` にする。`slug` が空なら comment-refresh が親から継承して row に書き戻す（full build も親から補う）。本文が空の承認済み row は描画しない。テンプレートとボタンは API で作れないので UI で作る
- Notion は integration（bot）が API で property を更新した event を `updated_properties: []` で送る。bot だけが author の event では comment-refresh を起動しない。import の `page.created` 3,000 件超で Workflow が大量に起動し、Notion の webhook 配信が一時停止されたため

### 投稿 API と通知

- Turnstile の `idempotency_key` は、request-id 単体ではなく request-id と token から派生した UUID にした（別 token の再送で同じ key を使い回さないため）
- `POST /api/comments` の親の確認は Turnstile の検証のあとにした
- SES は単一のメールアドレスではなく domain identity `mirumi.me` で送る。Outlook の迷惑メール振り分け対策として、DMARC（`p=none`）と Custom MAIL FROM（`bounce.mirumi.me`）も設定した
- SES の sandbox では、送信元だけでなく宛先の identity にも `ses:SendEmail` の許可が要る（送信元だけだと 403）
