
## 開発要素

- Cloudflare API サーバー
    - 記事更新差分ビルド API
        - Notion Webhook を受信して本文を取りに行く → Nuxt ビルド
        - POST エンドポイントで、pageId のパラメータを受けれるようにする（pageId は複数可）
        - バリデーション
            - slug が変わってしまっていないかチェックする
                - S3 の index.html かなんかにメタデータとして Notion の pageId を入れておいて、同じ slug で探したファイルの一致を確認する
                - 一致していなかったら API は成功で返しつつ「公開エラー」にセットして安全に終了する
        - バックアップは部分ビルドではなし
            - その記事のバックアップしか取れないとあまり意味はないし、かといってスナップショットの部分更新をできるようにするためだけにバックアップ全体のデータ構造を変えるのは理にかなっていない
        - ビルド自体は Workers の中ではできないので Cloudflare Containers を使う
            - Sandbox SDK はいらない
            - いままで CI 環境として用意していた実行環境を Dockerfile で用意するようにする
        - 上記のコンテナ起動は Cloudflare Queues からリクエストを出せばすぐにレスポンスを返せるし自動リトライなども面倒を見てもらえる
            - なので流れは Notion -> Workers -> Queues -> Containers になる
            - Queues は at-least-one なので重複排除や古い上書き可能性は実装側で防ぐ
            - ただし Queues Consumer の最大実行可能時間は 15 分までらしいのでこれは注意（部分ビルドなら現在の CI でも 2 分ちょいなので余裕なはず）
        - 画像同期
            - 編集後、公開するタイミングで Notion 上でアップロードされた画像を拾って S3 に配置
            - このとき各種リサイズ、必要であれば webp への変換も行う
                - いままではレンタルサーバーの PHP だから画像変換ができなかっただけで、すべての画像を webp に変換して完璧ハッピーなはず
                    - 既存画像どうしようかな（サイズ自動変換されたやつはだるいとしても、webp に変えるだけなら全部いけるかも？）
            - 変更検知とかはとくにやらず、普通に毎回全部同期する
                - キーは webp 変換後の画像を sha256 ハッシュしたものとする（put 前に軽く HEAD で存在確認すれば時間短縮できる）
            - 未使用画像を検知して削除する機能は当面はつくらない（たまにまとめて spark-joy すればよさそう）
        - サチコのインデックス API は再度有効化してシークレット生成してちゃんと管理して使うようにする
        - 公開停止も受け付けられるようにする
        - CI の re-generate は廃止
    - コメント受付
        - スパム対策（Cloudflare Turnstile を使う）
        - Notion へ書き込み
        - Application Passworkd をローテーションする
        - メール通知（1 日 1 回見れれば十分なので marumorumirumeri@outlook.com のほうでいい）
    - コメント更新差分ビルド API
        - コメントを承認なり返信したらフックする API
        - もしかしたら記事更新差分ビルド API と併用できるかも
    - シークレット管理に GitHub Actions secrets を使うのをやめる
        - そのプラットフォームが必要とするシークレットはそのプラットフォームで管理する

- フルビルド（通常のアプリケーションリリース）
    - いままで通り全記事フェッチはする
        - 後述するバックアップ用定期バッチでもおそらく同じ全記事フェッチロジックを使うので、レートリミットコントロール含めて共通化したい
        - プロパティから「編集したがまだ公開していない」記事だけフェッチから除外する
            - 除外には `nitro.prerender.ignore` を使う
    - バリデーション
        - 部分ビルドと同じように slug の変更有無チェックをここでもやる
    - S3 は全削除せず、生成したオブジェクトだけ上書きする
        - 除外記事の `{slug}/**` は削除・上書きせず、現在公開中のものをそのまま残す
            - 次に公開まで旧アプリケーション状態で配信されるがこれは許容する
            - 旧記事が参照する可能性があるため、ハッシュ付きの `_nuxt/**` も削除せず新旧を共存させる
        - 記事や不要アセットの削除は、フルビルドとは別の明示的な処理として行う
        - CloudFront の invalidation は通常どおり実行してよい

- バックアップ用の定期バッチ
    - Cloudflare Cron Triggers を使う
    - バックアップを 2 段階で取る（Notion 側の標準バックアップ(自動保存のこと)も含めると 3 段階）
        - Notion からの API レスポンスそのまま
        - パースして Vue コンポーネントに HTML として渡す直前の状態のもの
        - Block API からの変換ルート：
            - レスポンスをそのままレンダリングしたい HTML にする
                - 使うライブラリとしてはこれだけ（変換自体は自前実装）
                    - https://github.com/makenotion/notion-sdk-js
    - あとバックアップは R2 と S3 に取るようにすれば複数保管要件も満たせそう
        - R2 はよくわかってないのもあるが、S3 は Deeply Archive でよさそう

- Nuxt 4 へのマイグレーション
    - 主にビルドプロセスの高速化が目的
        - あと部分ビルドで `crawlLinks: false, routes: [###]` ってやってるやついい加減なんとかならんか
    - パッケージ類も上げられるだけ上げる、audit も通す
    - ついでに AI ベースでいいから全体のリファクタリングもやる

- 移行スクリプト
    - コンテンツブロックの対応づけが決定したらそれに応じた変換スクリプトをつくる
        - 作成前に全記事本文を取り直すのを忘れずに
    - もちろん WordPress 側のメタデータ類を Notion のプロパティに変換するのも含む

- プレビュー機能
    - Notion 側にプレビューボタンをつくる
    - Workers は実際の変換ロジックを実行して `Content-Type: text/html; charset=UTF-8` で生の HTML をレスポンスするだけ
    - 上記の HTML の中で mirumi.me で実際に配信されている css を参照するようにする
    - プレビュー URL は `https://mirumime.workers.dev/preview?slug=xxx` みたいな感じでいけないか？
        - ただし Notion のボタンは特定 URL を開くときに動的に組み立てられないため、下記のような Formula プロパティをつくっておくらしい：
            - `link("プレビュー", "https://mirumime.workers.dev/preview?slug=" + id())`
        - お手軽な認証として Cloudflare Access というのを使うとよさそうっぽい！
    - プレビュー中の画像だけは Notion API が返す一時 URL をそのまま使って表示する（本番 generate ではこれを S3 put した URL に差し替える）

- フロントエンド改善
    - 「みるめも？」のページがヘッダーのリンクごといらない気がする（ただしこれをなくすとサイト名を伝えられない問題があるんだよな）
    - ブロックごとなくしたので css 消していいものがけっこうある
        - rating_star
        - voice_wrap
        - speech_wrap
        - blank-box
        - keyboard-key
        - table-wrapper
    - X の Static Tweet block を再活用する！！
        - xAI API の x_search というやつを使う、一回 $0.005、同日内無課金
        - とはいえキャッシュは必須なので、KV にでも置いておく
            - key: `x-post:v1:<postId>`, value: `{"version": 1, "fetchedAt": "2026-08-06T00:00:00.000Z","post": {正規化した投稿データ}}`
        - あとたぶん UI のダークテーマはつくってなかったかも（どうせ Twitter -> X とか見直し要素はいろいろありそう）
        - あわせて X ウィジェットタグの読み込みとかもろもろゴミ掃除もできる！
    - ヘッダーまわりをよりシンプルにしたいね！
        - 中央寄せの趣味から左寄せの趣味に変わりそうな気もした
            - …と思ったけどまあいいかなあ
        - メニューの文字すら見えてなくてもいい気がしたんだよなあ
        - サイト名問題さえなくなれば「みるめも？」も消せるんだよな～（中身は不要）
    - 検索ページの改善
        - 検索後「記事がありません」ってなるやつ
        - 検索結果ページに戻ってきたりするとぶっ壊れてたりもする
    - 目次リンクを見出し名にしたい
        - 記事更新するとリンク先がずれる問題を直せる
        - 設計：
            - Notion の Block ID を使う（基本的な変更パターンすべてで大丈夫そう）
                - id は適当に base64 とかして先頭 7 文字でよさそう（接頭辞 1 文字くらいはあってもいい）
            - もし見出し階層が変わっても HTML の id で振っておけばそれもサポートできる
            - ただしこの方式では Notion 移行しないと id がわからない以上、事前に既存記事のリンク先を更新をすることはできない
                - でも別に数日間の目次リンクのリンク切れは全然許容できるので、単発の置換スクリプトをつくって移行後に置き換えればよい

## Notion 側の細かいカスタマイズ

- Notion 側でバリデーションをやれるのが理想だがここはまだ未検討
    - 公開ボタンを押して変えるのは「公開リクエストが OK で通った」という計算式のステータス変更だけで、そのステータス変更をもとにボタンではなくデータベース側のオートメーションを組めば実現できる
    - サムネイルが空 `?`「サムネイルがありません。自動生成サムネイルで公開しますか？」`:`「この記事を公開しますか？」

- 新規公開した記事に公開日をボタンからセットする
    - if(
        empty(現在のページ.公開日),
        now(),
        現在のページ.公開日
      )

- 「編集したがまだ公開していないフラグ」
    - Formula は補助表示のみ。公開開始時のページレベルの `last_edited_time` を保持し、デプロイ成功後、最終書き込み直前の再取得値と違えば成功扱いしない
    - 成功時は `最終デプロイ日時` の更新と `公開エラー` のクリアを最後の 1 回にまとめ、失敗時は短い理由と trace ID だけ残す
    - 公開処理から記事を書き戻すボットは `workers-api` のみ。再取得後の短い競合窓は許容し、同期状態や同期ログなどによる差分管理は持たない
    - 初回の本番デプロイに含まれた記事だけ、成功後に `最終デプロイ日時` を初期化する
